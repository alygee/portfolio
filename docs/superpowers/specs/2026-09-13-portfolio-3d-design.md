# Портфолио-сайт с 3D-сценой — дизайн

Дата: 2026-09-13
Автор: Альберт Аллагулов (совместно с Claude)
Статус: согласован, готов к планированию реализации

## 1. Контекст и цель

Персональный сайт-портфолио на основе резюме (Senior Frontend Developer,
9+ лет, React/TypeScript, highload, GIS).

**Главная цель — собственное развитие.** Проект задуман как лаборатория для
освоения WebGL/three.js/GLSL, которых в текущем стеке автора нет вообще
(стартовый уровень — нулевой). Пригодность сайта для найма — желательный
побочный эффект, а не критерий выбора решений.

Из этого следует главный проектный критерий: **максимум нового навыка на
единицу времени при минимальном риске заброса**. Риск заброса считается
основной угрозой проекту и влияет на архитектуру напрямую (см. §6).

### Критерии успеха

1. Автор написал и понимает собственный GLSL-шейдер, работающий на сайте.
2. Сайт задеплоен и остаётся работоспособным после каждой фазы.
3. Сайт читается и приносит пользу без WebGL и без JavaScript.
4. Бюджеты производительности из §7 соблюдены.

### Не-цели

- Не CMS и не блог. Контент правится в коде.
- Не бэкенд. Статический хостинг.
- Не мультиязычность на старте (архитектура ей не мешает, но задача не ставится).
- Не пиксельная точность к дизайн-макету: макета нет, эстетика вырабатывается по ходу.

## 2. Концепция

Две связанные сцены, выведенные из одних данных:

**A. Полёт по карьере.** Камера движется по 3D-кривой; скролл задаёт позицию на
кривой. Вдоль маршрута — четыре станции (AmazingCat → Поликод → Мобильная
платформа → ГИСГИС), у каждой разворачивается описание и метрики.

**B. Зал навыков.** Финальная точка маршрута — «галактика» стека: узлы-навыки,
сгруппированные в кластеры по категориям, рёбра — связи «навык применялся на этой
работе». Здесь скролл отдаёт управление орбитальной камере.

B не является отдельной страницей: это состояние сцены A.

## 3. Архитектура

### 3.1 Ключевые решения

**Р1. Контент вне сцены.** Типизированные данные в `src/content/` —
единственный источник правды. Из них рендерятся две независимые проекции:
семантический HTML-документ и 3D-сцена. Текст не дублируется в 3D-мире.

**Р2. HTML-проекция присутствует в DOM всегда**, а не только как fallback.
3D-слой располагается поверх. Отсюда SEO, доступность, печать в PDF и работа
без WebGL получаются без отдельной реализации.

**Р3. Один `<Canvas>` на приложение**, монтируемый лениво через `React.lazy` +
dynamic import. `three` уходит в отдельный чанк; главный бандл о нём не знает.
До загрузки виден статический постер.

**Р4. Разделы — это позиции камеры, а не роуты.** Сцена не пересобирается при
навигации. Хэш в URL синхронизирован с активной станцией, deep links работают
в обе стороны (вход по хэшу ставит камеру в нужную точку).

**Р5. Скролл не проходит через React-состояние.** Lenis → прогресс `0..1` →
транзиентная запись в Zustand-стор (`subscribe` без ре-рендера) → `CameraRig`
читает значение в `useFrame` и интерполирует камеру. React ре-рендерится только
при смене активной станции, а не на каждом кадре.

**Р6. `CameraRig` — единственный владелец камеры.** Преобразование
«прогресс → позиция и цель камеры» реализовано чистой функцией
`progressToCamera(t)`, тестируемой без браузера и без WebGL.

**Р7. Машина состояний сцены из двух состояний:** `travelling` и `docked`.
В `docked` скролл-привязка камеры отключается, включается орбитальный контрол.
Переход происходит на границах маршрута. Никаких разрозненных булевых флагов.

**Р8. Монтирование сцены решает один хук `useSceneEnabled()`.** При отсутствии
WebGL, при `prefers-reduced-motion: reduce` или на GPU tier 0 канвас не
монтируется вообще — не «сцена без анимации», а её отсутствие. Поведение
предсказуемо и проверяемо тестом.

### 3.2 Структура проекта

Облегчённый FSD: слои соблюдаются, строгость сегментов внутри слоёв — нет.
Полный канон FSD на проекте такого размера даёт больше церемонии, чем пользы.

```
src/
  app/              # композиция приложения, провайдеры, роутинг по хэшу
  content/          # данные резюме + типы (источник правды)
  entities/         # job, skill: типы и чистая логика над ними
  features/
    career-flight/  # сцена A: кривая, станции, CameraRig
    skill-galaxy/   # сцена B: граф, инстансинг узлов, picking
    scroll-bridge/  # Lenis, стор прогресса, синхронизация с хэшем
  shared/           # ui, hooks (useSceneEnabled), lib, конфиг сцены
```

### 3.3 Стек

Базовый стек выбран знакомым автору намеренно: вся новизна должна уйти в 3D,
а не в инфраструктуру.

- React 19, TypeScript, Vite
- @react-three/fiber, @react-three/drei, three
- @react-three/postprocessing (фаза 5)
- zustand (стор прогресса и состояния сцены)
- lenis (инерция скролла, десктоп)
- leva (отладка параметров сцены в рантайме)
- vitest, @react-three/test-renderer, @playwright/test, axe
- detect-gpu (определение класса GPU для деградации)
- Деплой: GitHub Pages (чистая статика, без внешних сервисов; переезд на другой хостинг тривиален)

## 4. Модель данных

```ts
type SkillCategory =
  | 'framework' | 'language' | 'build' | 'testing'
  | 'state' | 'backend' | 'database' | 'geo' | 'infra';

type Job = {
  id: JobId;
  company: string;
  url?: string;
  city: string;
  start: string;            // ISO YYYY-MM
  end: string | null;       // null = настоящее время
  role: string;
  summary: string;
  bullets: string[];
  stack: SkillId[];
  metrics?: { label: string; value: string }[];
};

type Skill = {
  id: SkillId;
  label: string;
  category: SkillCategory;
};
```

Граф сцены B выводится из этих же данных чистой функцией
`buildSkillGraph(jobs, skills) → { nodes, edges }`: `Job.stack` уже является
списком рёбер, `Skill.category` — готовым разбиением на кластеры. Отдельной
структуры под граф не существует.

Длительность работы и суммарный стаж считаются из `start`/`end`, а не хранятся
строками: иначе резюме устаревает молча.

Метрики из резюме («−30% багов на продакшене», «+40% скорости загрузки»)
визуализируются на станциях, а не только перечисляются текстом.

## 5. Поток данных

```
content/*.ts ──┬─→ HTML-проекция (всегда в DOM, семантическая разметка)
               │
               └─→ 3D-слой (lazy)
                     ├─ career-flight: progressToCamera(t) → камера
                     └─ skill-galaxy: buildSkillGraph() → инстансы узлов/рёбер

Lenis (или нативный скролл на мобильных)
   → scrollProgress 0..1 → zustand (транзиентно)
   → useFrame в CameraRig → lerp камеры
   → при пересечении порога станции: setActiveStation → ре-рендер React + хэш
```

## 6. Фазы реализации

Инвариант: **каждая фаза заканчивается задеплоенным работающим сайтом.**
Следующая фаза не начинается, пока предыдущая не задеплоена. Это прямая защита
от главного риска проекта (§9, Р-1).

| Фаза | Содержание | Осваиваемые навыки |
|------|-----------|--------------------|
| 0 | Сайт без 3D: контент-модель, HTML-проекция, вёрстка, деплой. `three` в проекте отсутствует. | — (знакомый стек) |
| 1 | `<Canvas>`, кривая маршрута, `CameraRig`, мост скролла, 4 станции примитивами + `<Html>`. | устройство R3F, `useFrame`, кривые, привязка скролла к камере |
| 2 | Среда: свет, туман, instanced-окружение, материалы, `leva`. | материалы и свет, instancing, первые оптимизации |
| 3 | Зал навыков: `buildSkillGraph`, instanced-узлы, рёбра, picking, `travelling → docked`, орбита. | инстансинг с данными, raycasting, состояние сцены |
| 4 | Первый GLSL: кастомный `shaderMaterial` для фона/частиц (uniform времени, vertex displacement, шум), затем GPU-частицы. | **GLSL, attributes, uniforms — главная цель проекта** |
| 5 | Постпроцессинг (bloom, DoF, виньетка), полировка, финальная проверка бюджетов и деградаций. | постпроцессинг, перф-бюджеты |

Фаза 1 намеренно поставлена сразу после фазы 0: связка «скролл ведёт камеру»
даёт впечатляющий результат за один-два вечера ещё до всяких шейдеров и
обеспечивает мотивацию на фазы 2-5. Шейдеры (фаза 4) сознательно отложены:
входить в GLSL следует в живом проекте с понятной целью, а не на чёрном экране.

## 7. Производительность и деградация

### Бюджеты

- Главный бандл без `three`: ≤ 100 КБ gzip.
- Чанк сцены: загружается лениво, вне критического пути.
- **LCP измеряется по HTML-проекции, а не по канвасу.** Текст первого экрана
  рендерится немедленно; сцена въезжает после. Портфолио разработчика,
  продающего оптимизацию Core Web Vitals, не имеет права на LCP из WebGL.
- Кадры: 60 fps на десктопе, не ниже 30 на мобильных.

### Средства

- `dpr={[1, 1.75]}`; `PerformanceMonitor` и `AdaptiveDpr` из drei снижают
  разрешение вместо просадки кадров.
- `frameloop="demand"` в состоянии `docked`, когда камера покоится.
- Инстансинг для всего, что повторяется (окружение, узлы графа).

### Деградация

`useSceneEnabled()` возвращает `false` и канвас не монтируется, если:

- WebGL недоступен;
- выставлено `prefers-reduced-motion: reduce`;
- `detect-gpu` сообщает tier 0 (WEBGL_UNSUPPORTED или BLOCKLISTED). Проверка
  выполняется один раз при инициализации, результат кэшируется на время сессии.

  Порог намеренно низкий. Шкала `detect-gpu` описывает его собственную тяжёлую
  эталонную сцену, а не нашу: на Intel Alder Lake GT2 под Mesa библиотека выдаёт
  tier 1, хотя сцена из четырёх примитивов идёт там свободно. Прежний порог
  tier ≥ 2 отсекал такие машины полностью. За качеством следит
  `PerformanceMonitor` по фактическим кадрам — это надёжнее, чем классификация
  по названию видеокарты.

### Мобильные устройства

На мобильных **инерция скролла не перехватывается**. Камера привязывается к
нативному скроллу документа. Перехват скролла на телефоне ломает нативные жесты
и ощущается хуже задуманного; анимация при этом остаётся той же.

## 8. Тестирование

Реализация ведётся через TDD. Архитектура §3 специально выносит логику в чистые
функции, чтобы это было возможно без браузера.

**Vitest (основная масса тестов):**
- `progressToCamera(t)` — позиция и цель камеры на границах и в середине;
- `buildSkillGraph(jobs, skills)` — узлы, рёбра, кластеры, отсутствие висячих ссылок;
- расчёт длительности работ и суммарного стажа, форматирование дат;
- переходы машины состояний `travelling ↔ docked`;
- `useSceneEnabled()` на мокнутых matchMedia и WebGL-контексте.

**@react-three/test-renderer:**
- `CameraRig` ставит камеру в ожидаемые точки при `t = 0 / 0.5 / 1`;
- станции монтируются в количестве, равном числу работ в контенте.

**Playwright (smoke, не более десятка проверок):**
- контент читается при отключённом JavaScript;
- хэш-навигация работает в обе стороны;
- горизонтального скролла нет на ширине 400px;
- axe не находит нарушений доступности;
- при `prefers-reduced-motion: reduce` канвас в DOM отсутствует.

**Явно не тестируется:** визуал пиксельными снимками. На 3D-сцене со временем,
шумом и постпроцессингом такие тесты нестабильны и не окупаются.

## 9. Риски

**Р-1. Заброс проекта на третьей неделе.** Главный риск: проект «для себя» без
внешнего дедлайна. Митигация встроена в архитектуру — фазовая лестница §6, где
каждая фаза деплоится, и вынесение первого впечатляющего результата в фазу 1.

**Р-2. GLSL как стена.** Нулевой стартовый уровень. Митигация: шейдеры отложены
до фазы 4, когда сцена уже живёт, и вводятся заменой одного материала, а не
переписыванием сцены.

**Р-3. Скролл-хайджек на мобильных.** Митигация: §7, на мобильных нативный скролл.

**Р-4. Отсутствие дизайн-макета.** Автор не дизайнер, эстетика вырабатывается
по ходу — есть риск бесконечной полировки. Митигация: одна выбранная
референсная эстетика на фазе 2 и запрет на её смену до фазы 5.

**Р-5. Сцена перетягивает бюджеты.** Митигация: §7, лимиты и ленивый чанк
фиксируются на фазе 1, а не в конце.

## 10. Объём планов реализации

Спека покрывает все шесть фаз, но **один план реализации на все фазы не пишется**:
фазы 2-5 зависят от того, что выяснится при работе над предыдущими, и
детализировать их заранее означало бы планировать вслепую.

Порядок такой: план пишется на фазы 0-1 (сайт без 3D плюс первый полёт камеры) и
доводится до задеплоенного результата. Затем — отдельный план на следующую фазу,
с учётом того, что уже выяснилось. Спека при этом остаётся общим ориентиром и
правится, если реальность расходится с ней.
