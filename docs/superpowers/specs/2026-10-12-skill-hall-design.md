# Зал навыков (фаза 3): траектория из веба в ML — дизайн

**Дата:** 2026-10-12
**Статус:** согласован в обсуждении, ждёт ревью владельца
**Родительская спека:** `2026-09-13-portfolio-3d-design.md` (§2 «Зал навыков», §4, §6 фаза 3).

## 1. Цель и аудитория

Владелец переходит из frontend-разработки в ML-инженеры по 48-недельному плану
(`docs/ml-engineer-plan.md`); на дату спеки идёт вторая неделя. Зал навыков
показывает нанимающему ML-тимлиду **траекторию**: откуда человек идёт (10 лет
продакшен-веба), куда (ML), что уже доказано делом и что переносится из
прошлого опыта в новую роль.

Учебная цель фазы из родительской спеки не меняется: инстансинг с данными,
raycasting, состояние сцены.

### Принятые решения

| # | Решение | Почему |
|---|---|---|
| З1 | Зал показывает траекторию: у навыка статус «применён» / «изучаю» / «в плане» | Честен на любой неделе плана; ML-кластер существует с первого дня |
| З2 | «Применён» выводится из доказательств (`stack` работы или проекта), не задаётся вручную | То же правило, что в черновике ML-резюме («только реально применённое»), но закреплённое кодом |
| З3 | Мосты — явный список в контенте с обоснованием `why` | Тимлиду нужна формулировка, а не подсветка; выражается в HTML без сцены (Р1/Р2) |
| З4 | Граф двудольный: навыки и хабы-доказательства (работы, проекты) | Ребро буквально означает «применён здесь»; хабы-работы — те же станции маршрута |
| З5 | ML-навыки — на уровне инструментов, как веб | Правило «применён = есть в `stack`» работает одинаково для обоих доменов |
| З6 | Зал исследуется в явном режиме по кнопке; в остальное время — подсветка из HTML | Документ лежит поверх канваса с `pointer-events: none`; на таче перетаскивание = прокрутка |
| З7 | Шапка документа («Senior Frontend Developer») в фазе 3 не меняется | Позиционирование — отдельное решение по `docs/strategiya-prodvizheniya.md`; называться ML-инженером на второй неделе рано |
| З8 | Зал — в конце долины, раскладка аналитическая и детерминированная | Единство сцены (B — состояние A), раскладка тестируется инвариантами; силовую можно подставить позже за тем же интерфейсом |

## 2. Контент-модель

### 2.1 Навык

```ts
type SkillCategory =
  | 'language' | 'framework' | 'state' | 'build' | 'testing'
  | 'backend' | 'database' | 'geo' | 'infra'          // веб
  | 'ml-data' | 'ml-classic' | 'ml-deep' | 'llm' | 'mlops'; // ML

type SkillIntent = 'learning' | 'planned';

type Skill = {
  id: string;
  label: string;
  category: SkillCategory;
  /** Только у навыка без доказательств. См. инварианты К1, К2. */
  intent?: SkillIntent;
};
```

Домен навыка не хранится, а выводится из категории:
`CATEGORY_DOMAIN: Record<SkillCategory, 'web' | 'ml'>` в `entities/skill`.
Пропуск категории ловит компилятор. `CATEGORY_LABELS` и `CATEGORY_ORDER`
дополняются пятью ML-категориями; существующий тест полноты `CATEGORY_ORDER`
продолжает действовать.

Подписи ML-категорий: `ml-data` — «Python и данные», `ml-classic` —
«Классический ML», `ml-deep` — «Deep Learning», `llm` — «LLM»,
`mlops` — «MLOps и сервинг».

### 2.4 Статус навыка

```ts
type SkillStatus = 'applied' | 'learning' | 'planned';
function skillStatus(skill: Skill, jobs: readonly Job[], projects: readonly Project[]): SkillStatus;
```

Чистая функция в `entities/skill/status.ts`, без `three`. `applied` — навык
встречается в `stack` хотя бы одной работы или проекта; иначе — `skill.intent`.
Используется и HTML-проекцией, и сценой: статус определён ровно в одном месте.

### 2.5 Инварианты контента (тесты)

- **К1.** У навыка без доказательств `intent` обязателен — иначе навык «ниоткуда».
- **К2.** У навыка с доказательствами `intent` запрещён. Добавил проект —
  убери «изучаю» в том же коммите; противоречие в данных не залеживается.
- **К3.** Мост: `from` — навык со статусом `applied` из домена `web`; `to` —
  навык из домена `ml`; пары `(from, to)` уникальны; `why` не пуст.
- **К4.** `stack` работ и проектов ссылается только на существующие навыки
  (уже обеспечено типом `SkillId`; тест на рантайм-данные остаётся).
- **К5.** `id` уникальны в пределах навыков, работ и проектов вместе — хабы и
  навыки живут в одном пространстве id узлов графа.
- **К6.** `Project.url` — абсолютный `https://`-адрес.

### 2.6 Стартовые данные

ML-навыки (18; на дату спеки `learning` только Python, остальные `planned`):

| Категория | Навыки |
|---|---|
| `ml-data` | Python, numpy, pandas |
| `ml-classic` | scikit-learn, CatBoost, LightGBM |
| `ml-deep` | PyTorch, Hugging Face Transformers |

Мосты (черновики `why`; формулировки за владельцем):

| from → to | why (черновик) |
|---|---|
| PostgreSQL → pandas | Агрегации и джойны над большими таблицами предбиллинга — те же операции, что в pandas |
| Docker → FastAPI | Упаковывал и выкатывал сервисы в контейнерах — модель за API выкатывается так же |
| CI/CD → MLflow | Строил пайплайны релизов; воспроизводимость экспериментов — та же дисциплина |
| Node.js → vLLM | Сервисы под нагрузкой: задержка, очереди, батчинг — ядро сервинга LLM |
| TypeScript → Python | Строгая типизация в большом коде переносится в type hints и mypy |
| Jest → evals | Внедрял тесты, снизившие баги на 30%; evals — тесты для моделей |

## 3. Граф

```ts
type GraphNode =
  | { id: string; kind: 'skill'; label: string; category: SkillCategory; domain: Domain; status: SkillStatus }
  | { id: string; kind: 'job'; label: string; domain: 'web' }
  | { id: string; kind: 'project'; label: string; domain: 'ml' };

type GraphEdge = { from: string; to: string; kind: 'applied' | 'bridge' };

function buildSkillGraph(
  skills: readonly Skill[], jobs: readonly Job[],
  projects: readonly Project[], bridges: readonly Bridge[],
): { nodes: GraphNode[]; edges: GraphEdge[] };
```

`entities/skill/graph.ts`, без `three`. Ребро `applied` идёт от хаба к навыку
из его `stack`; ребро `bridge` — от `from` к `to`. Хабы-работы — домен `web`,
хабы-проекты — `ml`.

Тесты: число узлов = навыки + работы + проекты; каждое ребро ссылается на
существующие узлы; навык имеет ребро `applied` ⇔ его статус `applied`; число
рёбер `applied` = сумма длин `stack`.

## 4. Раскладка

```ts
type Vec3 = { x: number; y: number; z: number };
function layoutGraph(graph: SkillGraph): Map<string, Vec3>;
```

`entities/skill/layout.ts`, без `three`, детерминированная (без случайности и
итераций до сходимости). Координаты локальные, относительно центра зала.

- Веб занимает полупространство `x < 0`, ML — `x > 0`; между ними разрыв
  шириной `GAP`.
- Центры кластеров (категорий) — на дуге в своей половине, порядок по
  `CATEGORY_ORDER`.
- Узлы кластера — на сфере Фибоначчи вокруг его центра; радиус растёт с числом
  узлов.
- Кластеры своей половины стоят по кольцу в плоскости `yz` вокруг оси
  половины (`x = ±X_OFFSET`); хабы — на малом кольце на той же оси, внутри
  большого. Рёбра `applied` расходятся от хабов к кластерам спицами.
  (Исходная формулировка «хаб в центроиде своих навыков» отвергнута при
  планировании: центроиды хабов-работ почти совпадают — все тянутся к оси
  половины — и хабы слипаются.)

Инварианты (тесты на настоящих данных и на синтетике):

- **Л1.** Любые два узла не ближе `MIN_DIST`.
- **Л2.** Каждый узел строго в своей половине (`x < −GAP/2` для веба,
  `x > GAP/2` для ML).
- **Л3.** Каждый мост пересекает плоскость `x = 0` (следует из Л2 и К3;
  проверяется явно).
- **Л4.** Все узлы внутри сферы `HALL_RADIUS`.
- **Л5.** Детерминизм: два вызова дают равные результаты.

Конкретные значения `GAP`, `MIN_DIST`, `X_OFFSET`, радиусов колец и
`HALL_RADIUS` подбираются в плане по инвариантам и проверяются глазами в
разработке.

## 5. Сцена

### 5.1 Место в мире

Маршрут продлевается одной точкой за последнюю станцию — **точкой
стыковки**: подъём от последней станции на длину обычного шага между
станциями (иначе прогресс по индексу разойдётся с длиной дуги, см.
`stationProgress`). Центр зала — на `HALL_DOCK_DISTANCE` дальше по оси
маршрута от точки стыковки, на её высоте. Зал висит над рельефом: его нижняя
точка выше вершины любого столбика под ним (тест на настоящих данных) —
площадка в рельефе не нужна.

Камера в режимах `docked` и `exploring` **не покидает точку стыковки** —
вращается сама галактика (§5.4). Поэтому поле рельефа расширять не нужно:
край мира остаётся в тумане по существующему тесту, бюджет
`MAX_TERRAIN_INSTANCES` не растёт. (Облёт камерой отвергнут при планировании:
кольцо облёта вынесло бы камеру за конец маршрута, и поле, чтобы край
остался в тумане, выросло бы до 6500–8800 столбиков при потолке 6000.)

Связь с туманом (тест): самый дальний узел от точки стыковки ближе
`fog.near + (fog.far − fog.near) / 2` — иначе дальняя половина зала тонет.

### 5.2 Визуальное кодирование

| Элемент | Реализация | Draw calls |
|---|---|---|
| Узлы-навыки | один `InstancedMesh`, икосаэдр, цвет по домену и статусу через `setColorAt` | 1 |
| Хабы | второй `InstancedMesh`, октаэдр, крупнее | 1 |
| Рёбра `applied` | один `LineSegments` с общей геометрией, приглушённый цвет | 1 |
| Мосты | второй `LineSegments`: дуги — дискретизированная квадратичная Безье над разрывом, бирюзовый акцент | 1 |

Зал добавляет ровно **4 draw call** (тест по образцу рельефа).

Цвет — по домену, а не по категории: веб — `foreground`, ML — `accent` из
`src/shared/config/palette.ts`. Четырнадцать различимых оттенков спорили бы с
эстетикой фазы 2 (один бирюзовый акцент на тёмном фоне); категорию передаёт
положение кластера и карточка. Новая палитра не вводится.

Статус — без настоящей прозрачности (не нужна сортировка инстансов):
`applied` — полный цвет домена; `planned` — цвет домена, смешанный с
`background` на 70% (`PLANNED_FADE`), — узел «тонет в тумане»; `learning` —
полный цвет домена и пульсация масштаба в `useFrame`, на фоне погашенных
`planned` он выделяется яркостью и движением.

Подписи — только в DOM (подсказка при наведении, карточка). 3D-текста нет:
troika заметно утяжеляет чанк, а текст по Р1 живёт в документе.

Подсветка (`highlightedId`, `selectedId`) — увеличение масштаба и осветление
цвета соответствующего инстанса; соседи по рёбрам не подсвечиваются (YAGNI).

### 5.3 Режимы

`entities/scene/sceneMode.ts` — чистый редьюсер; `sceneModeStore` — vanilla
zustand, без `three` (кнопка в главном чанке пишет в него).

```ts
type SceneMode = 'travelling' | 'docked' | 'exploring';
type SceneState = {
  mode: SceneMode;
  sceneReady: boolean;          // канвас смонтирован и сцена отрисовала кадр
  highlightedId: string | null; // только в docked
  selectedId: string | null;    // только в exploring
};
type SceneEvent =
  | { type: 'progress'; value: number }
  | { type: 'openHall' } | { type: 'closeHall' }
  | { type: 'highlight'; id: string | null }
  | { type: 'select'; id: string | null }
  | { type: 'sceneReady'; ready: boolean };
```

Переходы:

```
travelling ──progress ≥ 1 − DOCK_EPS──▶ docked ──openHall──▶ exploring
travelling ◀──progress < 1 − 2·DOCK_EPS── docked ◀──closeHall── exploring
```

- Гистерезис `DOCK_EPS` / `2·DOCK_EPS` против дребезга на границе.
- В `exploring` событие `progress` игнорируется.
- `openHall` допустим только из `docked` и только при `sceneReady`.
- `sceneReady(false)` из `exploring` возвращает в `docked` (сцена пропала —
  документ обязан вернуться).
- `highlight` вне `docked` игнорируется; `select` вне `exploring` игнорируется.
- Выход из `docked` сбрасывает `highlightedId`; выход из `exploring` —
  `selectedId`.

`progressStore` остаётся источником прогресса; мост между ними — подписка, которая
отправляет `progress` в редьюсер.

### 5.4 Камера

- `travelling` — как сейчас (`CameraRig`, `progressToCamera`).
- `docked` и `exploring` — `CameraRig` стоит в точке стыковки и смотрит в
  центр зала; переход из `travelling` сглажен `stepCamera`.
- Вращается группа зала, а не камера: состояние `{ yaw, pitch, скорости }`
  шагает чистой функцией `stepSpin`. В `docked` — медленное собственное
  вращение по `yaw`; в `exploring` — перетаскивание (мышь, палец) задаёт
  углы и скорость, после отпускания — инерция с затуханием; `pitch`
  ограничен. В `travelling` зал неподвижен (и кадр у маршрута стабилен —
  на этом держатся пиксельные e2e).
- `OrbitControls` не используется: новой зависимости в ленивом чанке нет.

Родительская спека (§7 «Средства») предписывает `frameloop="demand"` в
`docked`. Собственное вращение зала и пульсация «изучаю» требуют кадров, поэтому
`frameloop` остаётся `always`; качество по-прежнему держит
`PerformanceMonitor`. §7 обновляется (см. §10).

### 5.5 Режим исследования

Вход — кнопка «Открыть зал» в HTML-секции «Навыки». Она рендерится только при
`sceneReady && mode === 'docked'`: без WebGL, при reduced-motion или упавшем
ленивом чанке кнопки нет.

При входе:

- `html` получает класс `hall-open`: `main` — `opacity: 0` с переходом, затем
  `visibility: hidden`. **Не `display: none`** — схлопнется высота документа и
  потеряется позиция скролла (урок фазы 1.5).
- Скролл заблокирован (`overflow: hidden` на `html`; Lenis — `stop()`).
- Канвас получает `pointerEvents: 'auto'` — только в этом режиме; во всех
  остальных остаётся `none` (тест фазы 1.5 продолжает действовать).
- `history.pushState` — «назад» закрывает зал.

Взаимодействие:

- Перетаскивание по канвасу вращает зал (§5.4); у канваса `touch-action:
  none` только в этом режиме.
- Наведение и клик — события R3F на `InstancedMesh`; `instanceId` переводится в
  id узла таблицей, построенной вместе с инстансами. Наведение — подсказка с
  подписью; клик — `select`. Клик, завершающий перетаскивание (смещение
  указателя больше `CLICK_SLOP` пикселей), выбором не считается.
- Карточка — DOM-оверлей в ленивом чанке рядом с `<Canvas>`: подпись,
  статус текстом, «где применён» (хабы), мосты с `why`. Ссылка на хаб-работу
  закрывает зал и ведёт к `#<jobId>` — к станции.
- Доступность: оверлей — `role="dialog"`, `aria-modal="true"`, фокус на
  «Закрыть» при открытии и возврат на кнопку «Открыть зал» при закрытии;
  Esc закрывает; ←/→ перебирают узлы (клавиатурная альтернатива лучу) и
  озвучиваются через карточку.

Выход: Esc, кнопка «Закрыть», «назад» браузера, ссылка на станцию. Все пути
сводятся к `closeHall`, снимают `hall-open`, возвращают скролл в прежнюю
позицию.

### 5.6 Подсветка из документа

В `docked` наведение указателя на навык в HTML-списке отправляет
`highlight(id)`; уход — `highlight(null)`. Только указатель: пункты списка не
интерактивны, и делать фокусируемыми ~50 пунктов ради подсветки — значит
утяжелить навигацию с клавиатуры; клавиатурный путь к залу — кнопка
«Открыть зал» и стрелки в нём. Документ при этом виден и кликабелен, канвас
указателя не получает.

## 6. HTML-проекция

- «Навыки» — `<section id="skills">`; секция — последний якорь прогресса
  (якоря = работы в порядке `displayJobs` + `skills`). Инвариант
  `sectionsToProgress` («N-я секция в точке обзора ⇒ `stationProgress(N)`»)
  сохраняется; `#skills` работает как deep link тем же механизмом, что станции.
- Внутри — две группы по доменам: «Веб» и «ML». У каждого навыка статус
  текстовой меткой («изучаю», «в плане»; «применён» — без метки как
  умолчание), а не только цветом — доступность и печать.
- Подраздел «Что я переношу в ML» — список мостов: «PostgreSQL → pandas — why».
- Раздел «ML-проекты» (между «Опыт работы» и «Навыки») рендерится, только если
  `projects` не пуст.
- Кнопка «Открыть зал» — в секции «Навыки», см. §5.5.
- Шапка не меняется (З7).

## 7. Структура кода

Тест `featureBoundaries` запрещает фиче импортировать другую фичу, а `<Canvas>`
сейчас живёт в `career-flight/scene/SceneLayer.tsx`. Зал — отдельная фича,
поэтому сборка канваса поднимается в слой `widgets` (облегчённый FSD):

```
src/
  entities/
    skill/      status.ts, graph.ts, layout.ts (+ categories.ts) — без three
    scene/      sceneMode.ts (редьюсер), sceneModeStore.ts — без three
  features/
    career-flight/scene/   маршрут, CameraRig, станции, рельеф (как сейчас)
    skill-galaxy/
      OpenHallButton.tsx, useSkillHighlight.ts — главный чанк, без three
      scene/               SkillHall, HallNodes, HallEdges, HallControls (вращение), HallCard
    resume-document/       SkillList переработан под §6
  widgets/
    scene/      SceneLayer.tsx — Canvas, PerformanceMonitor, оверлей карточки;
                точка lazy(import) из App.tsx
```

- Правило Oxlint — каталожное по любому `**/scene/**` (фичи и виджет), а не
  только `career-flight/scene/`; override с разрешённым `three` — на те же
  каталоги. Подавление динамического `import()` в `App.tsx` переезжает вместе
  с путём.
- `featureBoundaries` расширяется: виджет может импортировать фичи; фича не
  импортирует виджет и другую фичу.
- `CameraRig` узнаёт про `docked` через `sceneModeStore` (entities), не через
  импорт из `skill-galaxy`.

## 8. Деградация и ошибки

- Нет WebGL / reduced-motion — канваса нет, `sceneReady` ложен, кнопки нет;
  HTML-раздел навыков со статусами и мостами полон.
- Ленивый чанк упал — `ErrorBoundary` рендерит `null`, `sceneReady` не
  выставлен, кнопки нет.
- Сцена упала в режиме `exploring` — `ErrorBoundary` в `widgets/scene` сначала
  отправляет `sceneReady(false)` и `closeHall`: документ возвращается, скролл
  разблокирован. Тест на это обязателен — иначе посетитель остаётся перед
  пустым экраном без прокрутки.
- `projects` пуст — раздела «ML-проекты» нет, хабов-проектов нет.
